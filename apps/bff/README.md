# apps/bff

Backend-for-frontend for apps/web. Aggregates calls into domains/ application layers for the web client's specific needs.

**Status: Implemented, wired to both domains currently built.** Real Fastify server, real Keycloak JWT verification (JWKS fetched live from Keycloak, ADR-0007/0012), wired to `@eta/domain-suppliers` (`/api/suppliers/*`) and `@eta/domain-procurement-core` (`/api/purchase-orders/*`).

The suppliers slice's HTTP/auth layer was verified live in an earlier session (not just unit-tested in isolation): `/health` public, `/api/suppliers/*` returns 401 without a token, a real Keycloak-issued JWT authorizes requests, the "no activation without certification" business rule was rejected with a real 400 then accepted after satisfying it. That verification predates [ADR-0017](../../docs/decisions/ADR-0017-single-source-of-truth-odoo.md) and checked persistence against Postgres, which this app no longer uses — re-verification against the real Odoo-backed repositories is still open.

**Persistence moved to Odoo (ADR-0017), superseding the Postgres schema-per-domain setup described here previously.** `main.ts` now opens one shared `OdooClient` (`platform/odoo`) instead of any Postgres connection — no migrations, no schema-per-domain config. Odoo connection settings live in `config.ts`'s `odoo` block (`ODOO_URL`, `ODOO_DB`, `ODOO_USERNAME`, `ODOO_PASSWORD`; url/db default to the real environment from ADR-0015 — `http://localhost:8069` / `eta_dev` — username/password have no default and must be supplied).

Local dev stack: Keycloak on 8080 (`docker compose up -d` still starts Keycloak/NATS; Postgres is no longer needed by this app). Realm/client/demo-user must be provisioned once against a fresh Keycloak (see conversation history for the admin-API calls used). The Odoo side additionally needs the `x_eta_id` custom fields described in `platform/odoo`'s README before end-to-end requests will actually persist.

**Known tooling gap (pre-existing, not introduced by the purchase-order work):** `nx run apps-bff:build` (and `nx run-many -t build` when it includes `apps-bff`) crashes with an internal TypeScript `Debug Failure` inside `resolveExternalModule`, whenever `apps/bff`'s tsconfig has a project reference to *any* `domains/*` composite project — reproduced on a from-scratch checkout with zero of this session's changes (suppliers-only, before procurement-core was ever wired in), so this is not a regression from this work. Root-caused to the `@nx/js:tsc` executor's specific invocation of the compiler, not to TypeScript itself: a plain `tsc --build apps/bff/tsconfig.json` (the standard project-references build command) compiles the whole workspace cleanly with real `.js`/`.d.ts` output. `typescript` was bumped from `5.6.3` to `5.9.3` in the root `package.json` as part of this investigation — a legitimate, low-risk fix in its own right, though it did not resolve the nx-specific crash. Until nx's build target is fixed or replaced (e.g. pointing it at `tsc --build` directly), use `npx tsc --build apps/bff/tsconfig.json` for a real compile/typecheck of this app, and `npm test` (vitest) for logic verification — both are clean.
